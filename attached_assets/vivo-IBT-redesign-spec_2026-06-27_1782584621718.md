# Vivo Fashion Group — IBT (Inter-Branch Transfer) Redesign
### Implementation specification — optimised for SOR + a shorter cash-conversion cycle

Prepared 27 June 2026 · front-end audit + 5-expert council (ratified 5/5) · Page: `/ibt`
Companion file: `vivo-IBT-redesign-wireframe_2026-06-27.png`.

---

## 1. Objective

Two goals, together:

- **Maximise SOR** = units_sold ÷ (units_sold + store stock) (warehouse excluded — the live formula).
- **Shorten the cash-conversion cycle (CCC).** IBT moves stock you have already paid for, so it adds **no new cash** — it should cut inventory days (DIO) by getting paid-for units to where they will actually sell.

Guiding principle the council kept returning to: **move the fewest units for the most incremental sell-through.** A transfer only helps if the unit sells *sooner* at the destination than it would have at the source, net of the days and cost of moving it.

---

## 2. Council verdict

A five-person panel (allocation/merch, supply-chain & working-capital, store-ops/fulfilment, BI/analytics, product/UX) **unanimously ratified** the redesign (5/5), each with one binding amendment, all folded in:

| Discipline | Binding amendment |
|---|---|
| Allocation / merch | **Curve completion is the ranking objective**, not a tie-breaker — rank moves first by whether they complete/extend a saleable size run at the destination, then by value. Velocity-floor on the destination. |
| Supply-chain / CCC | **Score every move by net CCC-days** (below), net of transport + duty; kill the "revenue uplift" headline; **markdown is a first-class alternative** when a move doesn't pay. |
| Store-ops / fulfilment | **Hub-through-warehouse by default** (direct store-to-store is impractical at 29 stores / 1 warehouse); **hard receiving-scan gate**; cross-border minimum ~24u, domestic ~4u. |
| BI / analytics | **One global solve** (assignment / min-cost-flow) over a shared destination-demand budget + donor-availability ledger that are *debited as moves are assigned* — architecturally prevents over-fill/over-commit; persist `_at_calc` snapshots. |
| Product / UX | **The unit of the screen is a from→to transfer bundle**, not a SKU row, carrying a two-sided lifecycle (Suggested → Scanned-out/in-transit → Scanned-in); delete blind "Mark As Done". |

## 3. Current state & defects

Live page: 300 open moves, 1,323 units, headline "Est. revenue uplift KES 5.94M". Rule: from-store sells ≤20% of the style's group average while holding stock; to-store sells ≥150% and is running low (≤2u); store-to-store only; clusters by revenue tier (A↔B, B↔C).

- **D1 — Destination over-fill (worst).** The to-store's 2-week cover gap is not shared across donor rows, so every source is told to send roughly the *whole* gap. One dress was suggested into **Vivo City Mall (sold 16/28d) = 46 units** from 5 sources; the same dress ~35 into Kisumu, ~26 into Moi Avenue. This converts a hot seller into dead stock at the destination — it **lowers** SOR.
- **D2 — Source over-commit.** Donor on-hand is not shared across its destination rows. **Kigali Heights (Rwanda, sold 2/28d) was told to ship 40 units** of one dress to four Kenyan stores — stock it cannot have.
- **D3 — No consolidation.** One row per (style, from, to). One sweater = **12 separate single-unit moves**; each is its own PO / "Mark As Done".
- **D4 — No geography/cost.** Suggests cross-border RW/UG↔KE moves (customs, freight); "clusters" are revenue tiers, not corridors.
- **D5 — Wrong scope.** "Online – Shop Zetu" used as a transfer source and destination; moves suggested *into* **Zoya Sarit** (a hard-retired brand).
- **D6 — Unusable + unreconciled.** Colour/Size/SKU/Barcode/Inv columns stuck at "Loading SKU details… 2%" (can't pick, can't verify source has stock); "Mark As Done" is a blind confirm; Days-lapsed blank; Completed-moves empty; no Odoo reconciliation. (Also note F17: the page must not mutate the global date filter.)

## 4. Core fix — one global solve, not a row-per-pair cross-join

The root cause of D1/D2/D3 is architectural. Replace the cross-join with a single optimisation pass per run over two authoritative, **decrementing** tables:

```
dest_demand[dest, sku, size]   = cover gap AFTER warehouse-deploy netting   (a budget, debited as assigned)
donor_ledger[source, sku, size] = on_hand − size_run_floor                  (debited as assigned)
```

Solve as an **assignment / min-cost-flow**: edges = (source → destination) for a sku/size, priced by net CCC-days (§5); each assigned move atomically debits both the destination budget and the donor ledger. A destination can never receive more than its gap (fixes D1); a donor can never promise more than it holds (fixes D2); **consolidation falls out** — group assigned moves by (source → destination) into one bundle (fixes D3). Cap moves per corridor per run so the solver can't ship marginal units just because an edge exists.

## 5. Move scoring & gates

**Net CCC-days (the value of a move):**

```
net_ccc_days = source_days_freed − dest_days_to_sell − in_transit_days
   source_days_freed = qty ÷ velocity(source, sku)      (high at a non-selling donor; cap at season-end days)
   dest_days_to_sell  = qty ÷ velocity(dest, sku)        (from the destination's demonstrated rate)
   in_transit_days    = corridor lead time (incl. cross-border customs dwell)
```

Move only if `net_ccc_days > 0`, and value it as **KES redeployed net of transport + duty**. This replaces the "est. revenue uplift" figure (which double-counts stock that may never sell).

**Ranking objective:** size-curve completion first (a single unit that turns a broken run into a sellable curve beats several units topping up cover), then net-CCC-days × value.

**Gates (all must pass):**

- **Demonstrated destination demand** — only move into a store with a proven sell-rate for the style; no imputed demand from cluster tier alone.
- **21-day newness guard** — a style gets 3 weeks to sell at a store before it's transfer-eligible, **both sides**. Apply to **full-price** newness only; **markdown/aged stock is exempt on the donor side** (clearance candidates should move to a proven puller rather than die on a slow shelf).
- **Minimum transfer** — domestic ≥ ~4 units; **cross-border ≥ ~24 units or landed-cost-vs-duty breakeven** (fixed customs/paperwork per consignment).
- **Size-curve integrity** — always leave ≥1 of each size on the donor's shelf.

---

## 6. Routing & coordination

- **Warehouse-deploy first (waterfall).** Run nightly in order: (1) if the central warehouse holds the SKU, satisfy destination need from there; (2) **net** that off each destination's gap; (3) **IBT last**, only on residual demand the warehouse can't cover. One shared destination-demand table consumed top-down so deploy and IBT never double-ship the same hot store.
- **Hub-through-warehouse by default.** Direct store-to-store is impractical and untracked; route moves through the warehouse (the only node with scanning/packing/reconciliation). Allow a **named exception** for two stores in the same mall/street (same-day walk-over).
- **Exclusions.** Online / Shop Zetu (demand-fed pool, not a donor/receiver); Zoya and any hard-retired brand as a receiver; EOL / dead-stock.

---

## 7. Markdown fork (CCC)

If a candidate has `net_ccc_days ≤ 0` **or** no qualified destination demand, the engine should **recommend markdown/clearance instead of a transfer** — surfaced inline on the bundle. For genuinely dead stock, marking down converts to cash now with zero transport, in-transit or cross-border drag; a transfer that may not sell only relocates the problem and *lengthens* CCC.

---

## 8. Metrics (replace "Est. revenue uplift")

- **Honest SOR uplift** (pp) from open bundles — bounded by what's actually pickable and demonstrated demand; the same metric is measured post-receipt.
- **Net CCC-days reduction** (avg per bundle and total).
- **KES of stock redeployed** (net of move cost) and **inventory-days removed**.
- Underpinned by a trustworthy **per-store-SKU velocity table with category-level shrinkage** (at ~0.2 u/wk most cells are sparse — shrink toward the category rate; distinguish "zero sales" from "no demand").

## 9. UI / UX redesign

**Fix first:** D6 — the Colour/Size/SKU/Barcode/Inv columns must actually load (server-side paginate); a transfer tool you can't pick from is non-functional.

**The unit of the screen is a transfer bundle (from → to), not a SKU row.** Each bundle expands to its SKU pick list. Two-sided lifecycle with a **hard receiving gate**: **Suggested → Scan-out (in-transit, stays on donor books) → Scan-in (received)**, with a **Discrepancy** branch when scan-in ≠ scan-out. Delete blind "Mark As Done" → it becomes **Scan-out** (prints a manifest/consignment id) and **Scan-in** (against that id). Stock stays on the donor's books until scan-in; SOR/inventory-days impact only realises on receipt.

**KPI tiles (replace "Est. revenue uplift"):** (1) Avg net-CCC-days reduction · (2) SOR uplift (pp) · (3) Bundles awaiting pick / awaiting receive · (4) Units in-transit (on donor books) · (5) Discrepancies / overdue receipts.

**Layout, top-to-bottom:**
1. Header: "As of today · 06:00 EAT" + a labelled "demand: trailing 28 days" pill (no date-range picker).
2. Five KPI tiles above.
3. Filter bar: brand, from/to-store, corridor/cluster, sensitivity, status.
4. Primary list — **one row per from→to bundle**, sorted by net-CCC-days / SOR-uplift×value; columns: From→To (corridor), SKUs, Units, Value, Net-CCC-days, SOR ▲pp, Status chip, Action.
5. Expand a bundle → SKU pick list (colour/size/SKU/barcode/inv FROM-TO/scan ✓) + inline **"Markdown instead"** on bundles that don't pay.
6. Action rail: Scan-out (donor) / Scan-in (receiver), manifest id visible.
7. Bottom: Received / Completed log, discrepancies flagged.

### Should IBT have a date range?

No reporting date range — it's an operational as-of-today worklist; a historical picker is meaningless and would re-create the F17 contamination bug. Provide one **labelled demand-lookback** (default 28 days, matching today's logic) that sets the velocity/sell-rate window, and ensure the page **does not mutate the global date filter**. The completed-moves log keeps its own history range.

## 10. Data foundation & reconciliation

Persist, per suggested move (immutable at calc time):

```
ibt_suggestion(run_id, run_ts_eat, from_loc, to_loc, sku, size, qty,
   source_onhand_at_calc, dest_gap_at_calc, net_ccc_days, transport_cost,
   curve_complete_flag, odoo_transfer_id, received_qty, received_ts)
corridor_leadtime(from_region, to_region, via_hub, lead_days)   -- refreshed from observed dispatch→receipt
```

State machine bound to an Odoo `stock.picking`: **suggested → approved → dispatched (Odoo validated) → in-transit → received**. The receiving scan writes `received_qty / received_ts`; in-transit ownership sits with the **warehouse/hub** (not source or destination) so neither store's SOR is distorted in flight. Completed-moves = `received_ts NOT NULL`; days-lapsed = `received_ts − dispatch_ts`; `received_qty ≠ qty` raises a discrepancy. Reconcile the suggestion ledger ↔ Odoo nightly on `odoo_transfer_id`. (Share this ledger with Replenishment so the two coordinate.)

## 10a. Live, event-driven data — the list must reflect reality

A suggestion is only useful if it reflects current state. Every relevant business event — a **sale**, a **stock movement**, a transfer **dispatch/receipt**, a **return**, a **price/markdown change**, a **new-style first sale** — must update the live state the engine reads, and the affected suggestions must be re-evaluated, so the screen never shows a move that reality has already invalidated (e.g. transferring a unit that just sold).

**Two layers (this resolves the snapshot-vs-live tension in §10):**

- **Immutable audit record** (`run_id` snapshot) — what was suggested and why, for measurement/accountability. Never mutated.
- **Live current-state store** — on-hand, in-transit, status, velocity — updated by events; this is what the screen shows and what is **re-validated at the moment of action**.

**Event → effect:**

| Event (from Odoo) | Effect on state & suggestions |
|---|---|
| Sale at a store | Decrement that store's on-hand; update rolling velocity/sell-rate; if the sold unit backed a suggested **donor** line, withdraw/reduce it; if at a **destination**, reduce its `dest_gap`. |
| New-style first sale at a store | Clears the proven-demand gate → style becomes transfer/replenish-eligible at that store. |
| Stock movement / GRN / warehouse receipt | Update on-hand; may resolve a stockout and retire suggestions. |
| Dispatch (scan-out) | Move qty to **in-transit** on hub books; remove from available pool; consume the soft-reservation. |
| Receipt (scan-in) | Flip to **received**; add to receiver on-hand; realise SOR/CCC impact; raise a discrepancy if qty ≠ dispatched. |
| Return | Increment on-hand; adjust velocity. |
| Price change / markdown / EOL flag | Reclassify; suppress from IBT/replenishment or route to the markdown fork. |
| New PO / production drop | Future-supply signal; may defer an IBT in favour of incoming warehouse stock. |

**No double-allocation (soft-reservation).** A unit can be committed to only one of {sale, IBT, replenishment} at a time. When a move is approved/picked, **soft-reserve** the donor unit (with a TTL); a concurrent **sale always wins** (it consumes the unit and the suggestion auto-withdraws and re-solves). A **shared reservation ledger across IBT + Replenishment** is the live form of the donor ledger (§4) and prevents the same unit being promised twice. **Re-validate at action time:** on Scan-out, re-check the donor still holds the unit; if a sale took it, block and re-suggest — this catches any event lag.

**Freshness model & SLA.**

- *State* (on-hand, status): near-real-time, event-driven — target < a few minutes.
- *Scoring stats* (velocity, SOR, net-CCC): rolling metrics — recompute on a short cadence (every ~5–15 min or per run); they don't need millisecond freshness.
- *UI:* show a live "as of HH:MM:SS EAT" indicator and per-row freshness; if the feed is stale beyond SLA, warn and soft-lock destructive actions. (This is the operational face of the Data Quality "sales sync lag" check — surface lag here, don't hide it.)

**Architecture (Odoo = system of record).** Capture via Odoo automated actions / webhooks or change-data-capture on `pos.order(.line)`, `stock.move(.line)`, `stock.picking` state, `account.move`, and product price/markdown → an event stream/queue. A consumer updates the live state store and triggers an **incremental re-solve of only the affected sku/store partitions** (not a full re-run); a **full re-solve runs nightly** as a backstop. Apply events **idempotently and in order** (event id + timestamp), and **reconcile against Odoo nightly** to heal any missed events — don't trust the stream alone (the audit already flagged sync lag). Build soft-reservation + action-time re-validation in Phase 1–2 (correctness); full event-streaming in Phase 3.

> Platform note: this live, event-driven model is not IBT-specific — apply the same pattern to **Replenishment** and the dashboards generally, so suggestions and KPIs reflect what is actually happening rather than a stale snapshot.

## 12. Open decisions (the knobs)

1. Minimum transfer sizes — domestic (≈4u) and cross-border (≈24u / duty breakeven).
2. Corridor lead-times and which corridors are allowed at all (cross-border on/off, or only above a higher net-CCC threshold).
3. Velocity window (default 28d) and the category-shrinkage strength for sparse store-SKU cells.
4. Same-mall store-to-store exception list (which store pairs bypass the hub).
5. The net-CCC-days threshold and the markdown cut-off.

---

## Expected impact

Consistent with the replenishment backtest finding that Vivo's network is **overstocked on a slow tail**: the near-term IBT win is **cash-conversion** — fewer, consolidated, demand-justified moves (and markdown instead of pointless transfers) cut inventory days and freight versus today's 1,323-unit, 300-move list. The **SOR** gain is concentrated where a move **completes a size curve** at a store with proven demand. The single biggest correctness fix — the global solve with shared caps — also stops the current design from *destroying* SOR by over-filling hot destinations (the 46-units-into-one-store problem). Validate with a backtest once store-SKU(-size) daily sales + stock snapshots and a corridor lead-time table are available.
