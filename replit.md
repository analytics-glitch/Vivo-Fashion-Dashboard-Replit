# Vivo Fashion Group BI

An executive Business Intelligence cockpit for Vivo Fashion Group — a multi-brand fashion retailer operating across East Africa (Kenya, Uganda, Rwanda, and an Online channel). It surfaces sales/revenue, locations & channels, footfall & conversion, customers, products, and inventory health from a live PostgreSQL database. All money is in Kenyan Shillings (KES).

## Run & Operate

- API server: runs `api_pg.py` (FastAPI) via the `artifacts/api-server` workflow — `uvicorn api_pg:app --host 0.0.0.0 --port 8080`, served under `/api`
- Frontend: `pnpm --filter @workspace/vivo-bi run dev` (previewPath `/`)
- `pnpm --filter @workspace/vivo-bi run typecheck` — typecheck the dashboard
- Required env: `DATABASE_URL` — Postgres connection string
- Health probes: `GET /api/healthz` is a DB-free **liveness** probe (always 200 when the process is up). `GET /api/readyz` is a **readiness** probe — 200 when the DB is reachable, **503** when it is not — and additionally reports the sync-loop heartbeat state (`ok`/`warning`/`critical`, or `starting` when no heartbeat exists yet so a first deploy still promotes). A stale heartbeat is reported but does NOT flip the HTTP status (a transient sync hiccup must not block a promotion). Both are public (whitelisted in `_AUTH_PUBLIC_EXACT`). The watchdog probes `/api/readyz` each health cycle for observability only — it never restarts on a DB blip (restart decisions stay on the DB-free liveness check + the heartbeat).
- Boot resiliency: all DB-touching startup work in `api_pg.py` (idempotent DDL/seeds) runs via the `_deferred_startup` decorator in ONE ordered background thread so uvicorn binds port 8080 immediately — a blocked DDL (orphaned-session locks after a deploy SIGKILL) once crash-looped prod by exceeding the platform's ~60s port timeout. New startup ensures must use `@_deferred_startup`, never a synchronous `@app.on_event("startup")`. The watchdog also port-polls the API (bounded 60s) before starting the sync loop.
- Pre-deploy code-health gate: `check_python_syntax.py` byte-compiles every top-level backend `*.py`. It runs both as a registered `compile` validation check and as a boot gate at the top of `watchdog.py`'s `main()` (after `ensure_table()`, before migrations/API/sync) — fails **closed**, so a syntactically broken backend (or an unrunnable checker) aborts startup and a deploy never promotes the broken version. This is the guard for the kind of botched-edit IndentationError that once crash-looped the sync.

### Production data is a SEPARATE database (dev rebuilds do NOT reach prod)

Development and the published deployment use **different** Postgres databases. The deployed api-server runs `watchdog.py` (Reserved VM, `WATCHDOG_MANAGE_API=1`), which supervises uvicorn **plus the incremental sync loop** against production's own DB. Production **never runs the full `transform_all_sales.py` rebuild** — only `sync_incremental.py` (recent days + a 4-day recovery backfill). So a full rebuild done in dev (e.g. to correct historical data) corrects the **dev** DB only; production's historical rows stay frozen at whatever logic last wrote them and never self-heal. Publishing ships code + migrates schema, but **does not copy data rows**.

Several auxiliary surfaces self-bootstrap their prod data from inside the incremental sync loop (so a fresh prod DB populates on first publish, then refreshes hourly): the fabric extract, the fabric-sheet override, and the **production tracker** (DPS buying orders → `production_orders` + `stage_movements`, feeding the `/api/production` board). The board's Waiting Sewing / Sewing / Finishing stages are **derived live from `all_inventory` Odoo stock locations** (Fabric Trimming → waiting_sewing; `Sew/Stock/A–E` → sewing, line = location suffix; Finished Goods Production → finishing) — the manual ledger only drives buying_order/cutting/washing/repairs/defects/warehouse, cutting's single action is "Clear" (→ waiting_sewing), and manual moves out of the live stages are 400-blocked (moves *into* a live stage, e.g. repairs→sewing or cutting's Clear, are allowed: they decrement the source in the ledger while the live stage's balance stays derived). The production-tracker step runs `sync_production_tracker.py`, which is idempotent (upsert on `order_ref`, intake appends only the delta) and ensures its own schema, so it is also safe to run as a standalone one-time backfill. The agent cannot publish or write to prod, so the board stays empty until the user publishes; verify after with a read-only prod query (`SELECT COUNT(*) FROM production_orders`).

**Product photos** (the dashboard style-table thumbnails + the `/gallery` page) come from `product_images` (base64 images, keyed by Odoo template) + `product_image_map` (SKU→template), populated by `extract_product_images.py` (an Odoo pull reading `all_products_clean`). The batch lookup `POST /api/thumbnails/lookup` (style_name → `/api/product-image/{sku}`) and per-SKU `GET /api/product-image/{sku}` resolve style→sku→template→image from these tables. This extract is now **self-bootstrapped from inside the incremental sync loop** (like the fabric extract / production tracker): on a fresh prod DB it runs once `product_images` is empty (after `all_products_clean` is populated), then refreshes every 24h (photos change rarely and it is the heaviest Odoo pull — a full base64 fetch per template). It is idempotent (`ON CONFLICT` upsert on tmpl_id/sku) and remains runnable standalone for a manual backfill. The agent cannot write to prod, so on the published app photos appear only after the next publish (the sync loop bootstraps them); until that first run prod rows fall back to the coloured-initials placeholder. Verify with a read-only prod query (`SELECT COUNT(*) FROM product_images`).

**Prod's source tables are NOT all complete** (the trap): the rebuild's transform reads `shopify_sales` (Shopify retail history) + `raw_shopify_vendor_sales` (Online) + `raw_odoo_*`. `shopify_sales` is populated ONLY by `shopify_full_extract.py` — the incremental sync never writes it — so on a fresh prod DB `shopify_sales` is **empty** and a transform-only rebuild silently drops ALL Shopify retail (Kenya pre-2026-03-20, Uganda, Rwanda → "Shopify deduped rows: 0"). Prod's `raw_shopify_vendor_sales` can also be doubled/un-netted (legacy data). So the rebuild MUST re-extract the sources first — do **not** skip the refresh.

To correct production's historical `all_sales`, use the **one-time rebuild gate** built into `watchdog.py`:

1. Set deployment secret `REBUILD_ON_BOOT=1` (Publishing → secrets). **Leave `REBUILD_REFRESH_RAW` at its default `1`** (do NOT set it to `0`) — that re-extracts ALL sources before the transform: `shopify_full_extract.py` → `shopify_sales`, `extract_shopzetu_sales.py --since=2022-01-01 --until=today` → `raw_shopify_vendor_sales` (un-doubles + re-nets via delete-by-window+insert), then `extract_odoo_products`/`extract_odoo_orders`, then `transform_all_sales.py` (TRUNCATE+repopulate, runs LAST so an aborted source refresh leaves `all_sales` untouched). Raise `REBUILD_TIMEOUT_SEC` (e.g. `7200`) since the first-time Shopify full extract is the long pole.
2. Publish (preferably off-peak — during the rebuild the live dashboard reads a partially populated table; a first-time full source extract can take well beyond tens of minutes). On boot the watchdog brings up the API (startup health passes), then runs the rebuild **synchronously before** the sync loop/health threads start so nothing overlaps it (an overlap would double history), then resumes normal supervision. Watch deployment logs for `Shopify deduped rows: <N>` being **non-zero** and `One-time full all_sales rebuild COMPLETED successfully`.
3. **Unset `REBUILD_ON_BOOT` (or set to 0) and republish** so it does not rebuild on every VM restart. (Going forward the incremental sync's delete-by-window + ON CONFLICT keeps Online from re-doubling, so this is a true one-time correction.)

Then verify prod via a read-only production query (e.g. Kenya net should match dev/BigQuery).

### Mobile (Android / Google Play) build via EAS

The Expo app (`artifacts/vivo-mobile`) is configured for EAS Build. **Before a production build, three things still require manual action (cannot be done from the agent):**

Build: `eas build --platform android --profile production`. Internal team distribution (recommended for this gated BI app) → use the `preview` APK profile or Google Play's internal testing track rather than a full public listing.

## Access & roles

- Authentication is a **custom Postgres email/password + Google OAuth** system (no Clerk, no Mongo, no Emergent). Identity + roles + approval status persist in the Postgres `app_users` table (`user_id`, `email`, `name`, `role`, `status` [pending|active|disabled|rejected], `auth_method` [password|google], `password_hash`, timestamps). Sessions live in `user_sessions` (`session_token` PK, `user_id`, `expires_at`). The session token is returned in the login JSON (frontend stores it in `localStorage` key `vivo_token` and sends it as `Authorization: Bearer`) and is also set as an httpOnly `session_token` cookie.
- Passwords use **stdlib PBKDF2-SHA256** (per-user random salt, 200k iterations, `hmac.compare_digest` constant-time verify) — NOT bcrypt/passlib (those wheels fail to build in this env). Google OAuth uses stdlib + `requests` (authorization-code flow with a `state` cookie for CSRF), NOT authlib/httpx.
- A seed admin is created idempotently on boot from `SEED_ADMIN_EMAIL` (default `admin@vivofashiongroup.com`) + `SEED_ADMIN_PASSWORD`. Google sign-ups whose email is on an allowed company domain land `store_manager`/`pending` and see the AwaitingApproval screen until an admin approves them. Admin-created users (`POST /api/admin/users`) are provisioned `active` immediately (creating them is the approval).
- Allowed company domains: `vivofashiongroup.com` and `shopzetu.com` (exposed via `GET /api/auth/allowed-domains`). Google callback requires `email_verified == true` AND an allowed domain.
- `api_pg.py` `clerk_auth_gate` middleware validates the session (Bearer or cookie) → `request.state.user`, returns **401** when unauthenticated, **fails closed (503 `auth_store_unavailable`)** if the user store is unreachable, blocks non-`active` users with distinct 403 details (`account_pending_approval` / `account_rejected` / `account_disabled` / `account_inactive`) so the frontend can route, allows the auth self-paths (`/api/auth/me`, `/me/status`, `/login`, `/logout`, `/heartbeat`, Google OAuth paths), and gates `/api/admin/*` to admins only. SQL-injection date-param validation runs for every `/api` request regardless of auth.
- Auth endpoints: `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `GET /api/auth/google/login`, `GET /api/auth/google/callback` (exchanges code → profile → domain check → provision → session → redirects to frontend `/auth/callback#token=…` or `#error=…`). The Google redirect URI defaults to `<scheme>://<x-forwarded-host>/api/auth/google/callback` and can be overridden with the `GOOGLE_REDIRECT_URI` env var. Requires secrets `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET`.
- Admin user management lives under `/api/admin/users` (list / approve / reject / role / enable-disable / delete / create as a local PBKDF2 user). Frontend admin page: `artifacts/vivo-bi/src/pages/Users.jsx`.
- Frontend gating: `src/lib/auth.jsx` (`AuthProvider` — `checkAuth` via `/auth/me`, `loginWithPassword`, `completeGoogleLogin(token)`, `logout`), `src/lib/api.js` (Bearer interceptor; 401 → `/login`), `src/components/ProtectedRoute.jsx` (loading spinner → `/login` if no user → AwaitingApproval if `status != active` → admin/page checks), routes wired in `src/App.js` (`/login`, `/auth/callback` public).
- Mobile gating (`artifacts/vivo-mobile`): the Expo app hits the **same** gated `/api`, so it has its own login. The login screen (`app/login.tsx`) is a visual replica of the web `Login.jsx` (brand row, allowed-domain subtitle from `GET /api/auth/allowed-domains`, **Google sign-in** + email/password). Google uses `expo-web-browser` `openAuthSessionAsync` with a runtime deep link from `Linking.createURL("/auth/callback")` passed to the backend as a validated `return` param (see `.agents/memory/mobile-google-oauth-deeplink.md`); `lib/auth.tsx` `completeGoogleLogin(token)` finishes the session. `lib/api.ts` maps transient gateway failures (502/503/504) + transport errors to friendly messages instead of raw "Request failed (502)". `lib/api.ts` keeps a module-level token (`setAuthToken`) attached as a Bearer header on every `apiGet`/`apiPost`; a 401 fires `onUnauthorized` → clears session → `/login`. `lib/auth.tsx` (`AuthProvider`) persists the token in `AsyncStorage` key `vivo_token`, restores it on launch via `/auth/me` (must be `status==='active'`), and clears the React Query cache on login/logout so a second user can't see prior figures. `app/_layout.tsx` redirect gate (loading spinner → `/login` if unauthenticated → `/(tabs)` once authenticated); `app/login.tsx` login screen; tab screens gate queries with `enabled: status==='authenticated'`; Overview has a sign-out button. See `.agents/memory/mobile-shares-api-auth-gate.md`.
- Mobile parity screens: beyond the 4 tabs (Overview, Markets, Products, Footfall) there is a **"More" tab** (`app/(tabs)/more.tsx`) — a grouped directory + sign-out linking to 10 stack routes that replicate the web analytical pages: `app/exec-summary`, `customers`, `rfm`, `margin`, `markdown`, `inventory`, `velocity`, `size-health`, `targets`, `data-quality`. Each is an auto-registered Expo Router stack route that sets its own title via `<Stack.Screen options={{title}}/>` and uses the native themed header (`app/_layout.tsx` Stack `screenOptions`). Heavy operational tools (Allocations/IBT/Replenishment/Re-Order/Range/Marketing/Custom Report/Exports/Feedback/Store Clusters) and admin (Users/Activity Logs) are intentionally NOT ported to mobile. Shared building blocks: `components/charts.tsx` (Donut/Legend/TrendLine/BarChart on react-native-svg) and `components/screen.tsx` (Screen scaffold, KpiGrid, MiniTable, Badge). Stack screens wrap their body in `<Screen onRefresh refreshing>`; date-scoped screens render `<PresetPills/>` + `useFilters().range`. Screens with multiple queries OR-compose loading/error (or use per-section states) so a partial API failure is never shown as healthy.
- Mobile Overview (`artifacts/vivo-mobile/app/(tabs)/index.tsx`) is a snapshot cockpit mirroring the web filter bar: top app bar (Vivo logo + brand + refresh/sign-out icons), an All/Retail/Online segmented control, a Share action (RN Share API), and tappable filter chips (date preset, compare period, country) backed by a Modal bottom-sheet; KES + POS chips are static. It shows a date-range + "vs <compare>" line, a "Mobile snapshot" pill with last-refreshed time (Africa/Nairobi), a dismissable stockout-alert banner, and a 2-col KPI grid (Total Sales [accent], Net Sales, Transactions, Units Sold with vs-period deltas + action pills that deep-link to /markets, /products, /footfall; plus Total Footfall and Conversion Rate). The Overview owns its **own local** filter state (preset default "today", compare default "last_month", country) so it does NOT re-scope the other tabs; the shared `lib/filters.tsx` provider stays preset-only (default "90d") for Markets/Products/Footfall. Deltas come from two `/api/kpis` calls (current + shifted compare range) since `/api/kpis` has no built-in comparison. The segmented All/Retail/Online and the Country sheet both write the `country` param (All=""/Retail="Kenya,Uganda,Rwanda"/Online="Online"; the sheet exposes a "Retail markets" option matching the combined value) because the backend's `channel` param is `pos_location_name` and cannot express Retail-vs-Online. See `.agents/memory/mobile-overview-filter-mapping.md`.
- Last-admin lockout guard + seed/bootstrap run inside one advisory-locked transaction (`_users_tx(lock=True)` + `SELECT … FOR UPDATE`) so concurrent requests can never leave zero active admins. See `.agents/memory/rbac-last-admin-toctou.md`.

### Social (Facebook Page) management

A staff Social surface lets the marketing team manage the brand's Facebook Page from the cockpit. Backend: `/api/social/*` in `api_pg.py` (status, diagnostics[read-only token/permission test], insights, posts, post[create], comments[+LLM sentiment], comments/{id}/reply) using a long-lived Page token + Page id from secrets `FACEBOOK_PAGE_ACCESS_TOKEN` / `FACEBOOK_PAGE_ID` against the Graph API (`_fb_get`/`_fb_post`, surface the Graph error message + 502 on failure). It is an **analyst+ surface gated server-side in `clerk_auth_gate`** (role ∈ analyst|exec|admin), the same way `/api/crm/*` is. Insights are **derived from the page node + recent posts** (summed reactions/comments/shares) rather than the version-fragile `/insights` metric API. Comment sentiment is assigned via the shared `_chat_llm` (positive/negative/neutral) and never blocks the response. Create-post + reply write `_crm_audit("social", …)`. Web frontend: `artifacts/vivo-bi/src/pages/Social.jsx` (page id `social`, route `/social`, nav under "Customers & Marketing", mirrors CRM.jsx styling). Web-only — not ported to the Expo app. See `.agents/memory/facebook-page-integration.md`.

The **clienteling CRM's** own Facebook sync (`POST /api/social/facebook/sync` in `crm_clienteling.py`, feeding the vivo-crm Inbox) deep-backfills the Page's history toward **cumulative** targets of ≥2000 stored posts, ≥2000 stored comments **and ≥2000 stored Messenger DMs**: newest-first pages of 100 posts with inline comment expansion, a 240s per-request budget, and persisted resume cursors (`crm_config` `social.fb.deep_cursor`/`deep_done` for posts, `social.fb.dm_deep_cursor`/`dm_deep_done` for conversations) so successive syncs continue where the last stopped; a non-blocking lock 409s concurrent runs; LLM sentiment runs only on new comments/DMs. DMs are inbound-only (`from.id != page_id`), stored as `type='dm'` rows (`fbdm:<msg_id>` source ids, sender PSID in `author_handle`, `fbconv:<thread>` parent); the Inbox reply for a DM sends a real Messenger message via the Send API and surfaces the actual Graph error (e.g. the 24-hour messaging window) as a 502 without stamping `replied_at`. A missing `pages_messaging` scope is reported in `scopes_missing` without failing the rest of the sync. Once targets are met a sync takes ~5-10s. `GET /api/social/feedback` clamps at 5000 rows and supports a `type=` filter (the Inbox loads 4000/type). See `.agents/memory/fb-sync-deep-backfill.md`.

## Architecture decisions

- The FastAPI backend aggregates on-the-fly in SQL against the live Postgres data, so cross-tabs (country/channel/product/store) stay internally consistent.
- The frontend is multi-page (6 nav sections) rather than a single scrolling page, with a shared filter bar that drives every page via React Query keys `[path, params]`.
- Endpoint filter contracts vary and the pages respect them: footfall & weekday-pattern take `date_from`/`date_to`/`channel` (no country); customer-trend / customers-by-location / stock-to-sales take `date_from`/`date_to`/`country`; churned-customers takes `days`/`limit` only.
- Cost discipline: React Query `staleTime` 5 min, `refetchOnWindowFocus` false.
- Filter date defaults/presets are formatted in local time (not UTC) to avoid an off-by-one around midnight in East Africa (UTC+3).

Endpoints: `GET /api/sops/departments` (counts + `can_upload`), `GET /api/sops/files?department=`, `GET /api/sops/files/{id}/download` (`?inline=1` for view), `POST /api/sops/upload` (multipart), `DELETE /api/sops/files/{id}`. All write rights are enforced server-side (`_sop_can_upload`, fails closed); the frontend flags only drive which buttons render. DDL is idempotent via `@_deferred_startup`, so prod self-provisions on publish. The `sops` page id is in `_VIEWER_PAGES` + every `DEFAULT_ROLE_PAGES` group (mirrored in `permissions.js`), so all department groups see it.

Per-chart CSV export is available throughout.

### CRM, Service & Loyalty

A CRM/CEM/loyalty surface sits on top of the same backend + auth. It is brand-aware via a `brand_code` split (`vivo` = Vivo #1a5c38, `sz` = Shop Zetu #7c3aed — shown as colored dots, no logos).

- Backend: ~30 endpoints under `/api/crm/*` in `api_pg.py` (inserted before the `StaticFiles` SPA catch-all). Schema is idempotent DDL (`_ensure_crm_tables()` on startup) — 14 `crm_*` tables (config, customer overrides + manual contacts, tags + members, tasks, interactions, campaigns + members, tickets + messages, loyalty enrolment, append-only ledger, redemptions, audit). Customers blend the read-only `all_customers`/`all_sales` data with the `crm_customer` override row (FULL OUTER JOIN) so manual contacts and CRM edits coexist with transactional history. Loyalty config defaults (earn rate, point value, tiers, channel/priority SLAs) seed from config. **External features deferred**: social webhooks, POS/Shopify auto-sync, customer-facing loyalty app, OTP, email engine, ML churn.
- Web: single `src/pages/CRM.jsx` with tabbed sub-views (Contacts/360, Tasks, Tickets, Campaigns, Loyalty, Config[admin]). Route `/crm` in `App.js`, nav under a "Customers & Marketing" group in `navItems.jsx`, page id `crm` in `permissions.js`.
- Mobile (`artifacts/vivo-mobile`): a "CRM" group in `app/(tabs)/more.tsx` (gated to analyst+ roles) linking 4 lighter stack screens — `app/crm-contacts.tsx` (search + segment filter), `crm-customer.tsx` (360 view), `crm-tasks.tsx` (queue + mark-done), `crm-tickets.tsx` + `crm-ticket.tsx` (list/detail, status change, reply), `crm-loyalty.tsx` (summary + member lookup). `lib/api.ts` gained `apiPatch` (shared `apiWrite` helper with `apiPost`); brand dot/label helpers live in `constants/colors.ts`.
- **Authorization**: CRM is an analyst+ surface. The `clerk_auth_gate` middleware enforces `role ∈ {analyst, exec, admin}` for any `/api/crm/*` request server-side (so hidden web nav / mobile routes can't be bypassed); finer-grained mutations (loyalty adjust, config PUT) still require admin via `_crm_is_admin`.

#### Customer-facing loyalty (Carrefour-style membership card)

A self-service loyalty layer lets shoppers enrol, view their tier/points, and redeem **without any staff login**, plus a scannable membership barcode the POS scans to earn points. It reuses the same backend + branding + KES; points/tiers live in the existing `crm_loyalty_enrolment`/`crm_loyalty_ledger`/`crm_redemptions` keyed by the member's `customer_id`. See `.agents/memory/loyalty-member-card.md`.

- **Member identity** is distinct from staff `app_users`: table `crm_loyalty_member` (`member_id` PK = `customer_id` = `mbr:`+hex, `brand_code`, `name`, `phone` UNIQUE, `email`, `membership_code` UNIQUE [13-digit barcode], `pin_hash`, `card_token_hash`, `spend_kes`, `failed_logins`/`locked_until` for login throttle). PIN reuses the staff `_hash_password`/`_verify_password` (PBKDF2); the device card token is sha256-hashed at rest and sent as the `X-Member-Token` header. Enrol mirrors the member into `crm_customer` (`is_manual`, `created_by='loyalty:self'`) + `crm_loyalty_enrolment` so staff 360/loyalty views see self-enrolled members.
- **Public endpoints** `POST /api/loyalty/{enrol,login,logout,redeem}` + `GET /api/loyalty/me` are **bypassed in `clerk_auth_gate`** (member-token auth, not staff session) — they are the ONLY non-`/api/crm/*` loyalty paths and members still cannot reach staff `/api/crm/*` data. `login` (phone + 4–6 digit PIN) is brute-force throttled: 5 consecutive bad PINs lock the account for 15 min (returns 429), tracked on the member row inside an advisory-locked tx; unknown phone returns the same 401 as a bad PIN (no account enumeration).
- **Tiers, earn multipliers & points expiry**: four loyalty tiers by spend (KES, PRD v3 §5.3) — Bronze 1–49,999, Silver 50,000–149,999, Gold 150,000–299,999, VIP 300,000+ (`_crm_tier_for_spend`). VIP is a real loyalty tier (`loyalty.tier_vip_kes`=300000) AND still gates the CRM "vip" high-spender segment. Earn rate is tiered: `loyalty.earn_multiplier_{bronze,silver,gold,vip}` = 1/2/3/4 pts per KES 100 (`_crm_earn_multiplier`); the earn endpoint uses the member's pre-purchase tier. (PRD §6.2 wants *flat* 1pt/KES100 at launch — flat-vs-tiered is an open finance decision; infra kept.) Points expire after `loyalty.points_expiry_months` (12) of no `earn` activity via `_member_expire_inactive_points` — lazy (no cron), run on `GET /api/loyalty/me` and at earn-time (returning resets the clock), writing an `expire` ledger row. `GET /api/loyalty/me` `config` returns `points_expiry_months`, `tiers` {Silver,Gold,VIP} and `earn_multipliers` {Bronze,Silver,Gold,VIP}. Config lives in the `crm_config` DB table (overrides `CRM_CONFIG_DEFAULTS` via `ON CONFLICT DO NOTHING`), so changing defaults requires UPDATE-ing existing rows too; after a threshold change POST `/api/loyalty/recompute` (admin) to re-tier enrolments. See `.agents/memory/loyalty-tier-rules.md`. Web app `artifacts/vivo-loyalty` shows the Vivo logo (imported via `@assets/...`) on Home/Login/Enrol and a "Tiers & Rewards" card with thresholds, per-tier earn rates, and the expiry note.
- **Staff POS earn** `POST /api/crm/loyalty/earn` (analyst+) scans `membership_code` + `amount_kes` → floors points by `earn_rate_kes`, applies the tier multiplier, updates spend + tier, writes ledger + audit, returns the member name + `points_multiplier` for POS confirmation. **Idempotent on `transaction_id`** as a hard DB invariant: a partial-unique index `uq_crm_ledger_earn_txn` on `crm_loyalty_ledger(customer_id, transaction_id) WHERE reason='earn' AND transaction_id IS NOT NULL` + `INSERT … ON CONFLICT DO NOTHING` makes concurrent same-txn requests collapse to a single credit (the loser returns `duplicate:true` with the existing balance). A manual staff award with NO `transaction_id` always credits (each is intentional; double-tap guarded client-side).
- **Mobile customer flow** (`artifacts/vivo-mobile`): `lib/member.ts` (token in AsyncStorage key `vivo_member_token`, `memberGet`/`memberPost` send `X-Member-Token`); barcode rendered with `react-native-barcode-svg` (CODE128, on react-native-svg). The `app/member/` group (`index` card = barcode + tier + points + KES worth + lifetime + redeem + ledger activity; `enrol`; `login`) is reachable **while the staff app is unauthenticated** — `app/_layout.tsx`'s redirect gate allows `segments[0]==="member"` (like `login`) and registers `<Stack.Screen name="member" headerShown:false/>`. Entry link on `app/login.tsx` ("Loyalty member? View your card").
- **Staff "award points by code"** UI exists on both the web CRM Loyalty tab (`src/pages/CRM.jsx` — code + amount inputs → `POST /api/crm/loyalty/earn`) and mobile `app/crm-loyalty.tsx` (Award Points card).
- **Staff "redeem code at till"** closes the redeem loop: members redeem points (in-app / web) and get a `discount_code` (`VFG-XXXXXXXX`) stored `code_status='issued'` in `crm_redemptions`. At the till, staff `POST /api/crm/loyalty/redeem-code/lookup` (read-only preview: member name + KES value + status) then `POST /api/crm/loyalty/redeem-code/apply` (analyst+) which marks the code `used` inside a `SELECT … FOR UPDATE` tx → **single-use** (concurrent/second apply returns 409, unknown code 404). Points were already deducted at issue time, so apply only burns the code + surfaces the KES discount. UI: validate→apply card on web CRM Loyalty tab + mobile `app/crm-loyalty.tsx` "Redeem Code" card.
- **Redemptions report** `GET /api/crm/loyalty/redemptions/report` (analyst+) tracks loyalty discount spend over time: summary (codes issued / open / used, KES issued / used / open, points redeemed), a per-store breakdown of realized spend, and a recent-codes list. **Two date dimensions** — issued/outstanding metrics scope by `issued_at`; codes-used + KES-spent + by-store scope by `used_at` (so a code issued before the window but redeemed inside it counts as in-window spend). Optional `date_from`/`date_to` (both required together or 400; omit both = all-time). UI: report card on web CRM Loyalty tab (KPI tiles + by-store table + recent-codes table + date picker) and a mobile `app/crm-loyalty.tsx` "Redemptions Report" section (KPI grid + by-store list, all-time).
- **Member message inbox** — staff broadcast in-app announcements/offers to loyalty members; members read them inside the mobile membership card. Tables `crm_member_message` (`audience` `all|brand|member`, optional `brand_code`/`customer_id`, `active` for soft delete) + `crm_member_message_read` (PK message_id+customer_id). Audience matching lives once in `_member_message_match_sql()` (cols qualified `msg.` to avoid ambiguity with the joined read table); reused by the member list, `_member_unread_message_count()`, and `unread_messages` on `GET /api/loyalty/me`. **Public member endpoints** (X-Member-Token, bypassed in `clerk_auth_gate`): `GET /api/loyalty/messages` (list + unread, `active=TRUE` only), `POST /api/loyalty/messages/{id}/read` (idempotent `ON CONFLICT DO NOTHING`). **Staff endpoints** (analyst+): `GET/POST /api/crm/member-messages` (list shows reach + read_count incl. retracted; create validates title/body/audience, member-audience checks customer_id exists), `DELETE /api/crm/member-messages/{id}` (soft delete). UI: web CRM "Messages" tab (`src/pages/CRM.jsx` — list + compose modal with audience selector + retract) and mobile `app/member/messages.tsx` inbox (tap to mark read) with an unread badge on the member card (`app/member/index.tsx`). **Scheduling**: optional `publish_at`/`expires_at` (TIMESTAMPTZ) columns auto-publish/auto-hide offers with NO cron — visibility is time-gated in SQL via `now()` inside `_member_message_match_sql()`, so a message simply starts/stops matching. The web compose modal sends `datetime-local` as UTC ISO; the staff list derives a `status` (active/scheduled/expired/retracted) shown as a colored Pill with the publish/hide times.

## Gotchas

- JOIN RULE (user-mandated): any join between `all_sales`, `all_inventory` and `all_products_clean` MUST be on SKU (`s.variant_sku = p.sku`, `i.sku = p.sku`; barcode acceptable) — NEVER on `style_name`. ~16.7k `all_inventory` rows have a blank `style_name`, so name joins silently zero stock. Reach inventory/sales for a style by expanding to SKUs via the product master first, and take dims (size/colour/brand) from the master. See `.agents/memory/triad-joins-sku-only.md`.

- ENVIRONMENT: if the `u-root-cmds` Nix package is present in `.replit` `[nix].packages`, it shadows GNU coreutils (`find`, `ls`, `sort`, `head`, `tail`, ...) with stripped-down versions. This breaks search/glob tooling AND the agent checkpoint/save step (fails with `UNKNOWN_NOT_GIT`). Remove it and fully restart the Repl. See `.agents/memory/uroot-find-breaks-checkpoint.md`.
- DEV-ONLY HMR ghost: `src/lib/filters.jsx` exports both the `useFilters` hook and components, which breaks React Fast Refresh. Editing it (or co-editing) prints `Invalid hook call` / `useFilters must be used inside FiltersProvider` then forces a full page reload that recovers. These are NOT runtime bugs — production has no HMR. They masquerade as a "stuck on skeleton / Loading…" bug, especially since each screenshot is a fresh page load that captures the pre-data loading state. Trust the console `loading:false … hasKpis:true` line over a transient skeleton screenshot. See `.agents/memory/hmr-fast-refresh-ghost.md`.
- `all_sales.sale_date` is a TEXT column. `BETWEEN '...' AND '...'` works, but date functions (`date_trunc`, `EXTRACT`) need an explicit `s.sale_date::date` cast or they error with `function date_trunc(unknown, text) does not exist`. See `.agents/memory/pg-text-date-columns.md`.
- DATA: `pos_location_name = 'vivowoman'` is the PRIMARY Kenya POS (~84% of all sales, all pre-Feb-2022 data). It must NOT be excluded in `api_pg.py` `BASE_FILTERS` or history/Kenya sales go missing. Keep excluding only `Staff purchases`/`Manual Order`/`Online - vivo-uganda`. See `.agents/memory/vivowoman-base-filter.md`.
- Churn (doc 5): churned = no transaction in the last 90 days; rate = churned / eligible base (customers whose first purchase is older than 90 days). Defined identically in `/api/customers` and `/api/customers/churn-rate`. The rate is legitimately high (~97%) because the dataset is largely historical relative to today; this is correct, not a bug.
- Recharts: a Pie with a bottom Legend can collapse its radius to ~0; pin `cx`/`cy` + radii and constrain Legend height. See `.agents/memory/recharts-donut-collapse.md`.
- The legacy Express api-server, `lib/api-spec/openapi.yaml`, and the Orval-generated `lib/api-hooks`/`lib/api-zod` are no longer wired into the running app (kept only as leftover scaffold).
- FABRIC: Odoo's `raw_fabric_moves` had badly inflated Jan–Apr 2026 consumption/returns (e.g. ~2.2M kg fake March production returns). The buying team's reconciled Google Sheet overrides OUT (consumption) and production returns (INTERNAL from `Virtual Locations/Production`) for 2026-01-01..2026-04-30 ONLY; IN is always Odoo, and May 2026+ / pre-2026 stay Odoo. Every Fabric view reads the `fabric_moves_effective` view (raw minus in-window OUT/prod-returns, UNION sheet rows) instead of `raw_fabric_moves`, so the override survives the hourly Odoo TRUNCATE rebuild. Loader `extract_fabric_sheet.py` (also hooked into `sync_incremental.py`, hourly + bootstrap) populates the separate `fabric_sheet_*` tables on the prod DB. See `.agents/memory/fabric-net-consumption.md`.
- FABRIC LIVE VIEWERS: the standalone Fabric dashboard (`/fabric`) shows a realtime "N viewing now" presence pill (green pulsing dot) with an expandable popover of who's online (name + role) for any signed-in user. No WebSockets — the page pings `POST /api/auth/heartbeat` (`{page:"fabric"}`, Bearer `vivo_token`) every 15s to stamp its own `user_sessions` row (`last_active_at`/`last_active_page`, added idempotently in `_ensure_users_table`) and polls `GET /api/auth/active-viewers?page=fabric` every 8s. The endpoint returns distinct active users (deduped per `user_id`, `status='active'`, `last_active_at` within a 45s window) with name + role only (no PII), and is best-effort (empty list on error). Heartbeat/poll pause on `document.hidden` so idle/closed tabs drop off within the window. All interpolated user text is `esc()`-escaped before `innerHTML` (fabric XSS precedent). Fabric-only — not wired into any other surface.
- FABRIC CHANGE LOG: the three buying-team reservation write actions on the Fabric dashboard (create / mark-used / delete `/api/fabric/reservations*`) each append one human-readable, append-only row (Timestamp EAT, user name/email, action, reservation id, fabric/product, style, qty, uom, note, resulting status) to a running Google Sheet for an audit trail. Module `fabric_change_log.py` (write helper `_gsheet_append` in `hr_attendance.py` via Sheets v4 `values:append`, USER_ENTERED/INSERT_ROWS); it auto-writes the header on first write and is **strictly best-effort** — runs in a daemon thread after the DB commit, NEVER blocks/raises the dashboard action (a failed append is server-logged only). Config: set deployment secret `FABRIC_LOG_SHEET_ID` (optional `FABRIC_LOG_SHEET_TAB`, default `Sheet1`); when unset the whole feature is a no-op. **Manual prerequisites (no Drive scope in code):** the user creates one blank Sheet inside their Drive folder and supplies its id; the connected `google-sheet` integration must have EDIT (write) scope; and that Sheet must be shared as Editor with the connected Google account or appends 403.
